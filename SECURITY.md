# Security / Sécurité — 0.3.0

## Security boundaries (English)

This is a development release, not a security certification or a claim of being unhackable. Original Rust code forbids `unsafe`; dependencies use native code where needed (SQLCipher, OpenSSL, graphics and window effects).

### Local encryption

Persistent profiles always require an encryption key. Default system mode generates a random secret from three OS-random UUIDv4 values and saves it in native Windows Credential Manager (macOS Keychain on macOS). A non-secret random `device-key-id` in the profile identifies that entry; no key is stored beside the database. Missing credentials for an encrypted profile never cause key regeneration or database replacement. Unsupported platforms fail closed rather than using a mock/plain file backend. This native integration is compiled for Windows, but actual Windows Credential Manager operation is not yet verified on a Windows host.

Optional master mode requires a passphrase of 12 or more characters, up to 1024 UTF-8 bytes, without NUL. The sync account password is never used as the SQLCipher key. Local encryption is independent of login, password rotation, network/VPN availability and Joplin E2EE. SQLCipher **4.19.0**, built with vendored OpenSSL **3.6.3**, uses its SQLCipher 4 defaults: AES-256-CBC page encryption, per-page authentication and PBKDF2-HMAC-SHA512 key derivation (256,000 iterations). The application does not implement its own cipher or KDF. The database, attachments, revisions, drafts, search indexes, settings and WAL page content are encrypted. `temp_store=MEMORY`, foreign keys, full synchronous commits and a per-profile OS file lock are enabled.

Passphrases are not put in environment variables, process arguments, settings or log files. The retained vault secret and UI passphrase buffers use `zeroize`; SQLCipher memory wiping is enabled. These are best-effort protections, **not a guarantee that all copies of note content or secrets are wiped from RAM, GPU memory, swap, crash dumps or the OS clipboard**. Data must exist in memory while unlocked. A compromised OS or administrator can access a running process.

Manual and idle locking drop the open profile and clear UI/image caches. System mode defaults to no idle locking; master mode defaults to five minutes, configurable 0–60 (0 disables it). System-mode reopening uses the OS credential without per-open Windows Hello authentication. A same-user process may access that OS credential; app locking in system mode is a display/privacy convenience, not a separate authentication boundary. Lock the OS session when away. Both monotonic and wall-clock elapsed time are checked, including a return from suspend. Invalid unsaved drafts are stored encrypted before closing; if that write also fails, locking is refused to preserve the visible draft. A lock during sync hides the workspace and asks the worker to cancel; an in-flight HTTP request, and subsequent lock release, may take up to their timeouts before the worker drops the real database/key. The displayed lock screen does not claim immediate zeroization of an active network worker.

### Migration, backups and password changes

A legacy Carnet Rust plaintext profile is schema-checked, exported directly into an encrypted temporary database, integrity-checked, and atomically substituted only after success. The original stays active on an earlier failure. WAL is checkpointed before replacement. Orphaned recovery journals are never treated as an empty new vault. No plaintext rollback copy is made. **This does not securely erase previously allocated disk blocks, external backups/exports, OS snapshots or file-system history.** The official Joplin profile is not opened or changed.

User-created portable backups now require a separate export passphrase, so they can be restored without the original device credential. Automatic recovery snapshots use the key current when created. Before replacing a system key with a master passphrase, a portable recovery snapshot is written under the new passphrase. Previously generated automatic snapshots under the retired system key do not acquire that new passphrase. Restore validates the backup and preserves an encrypted recovery copy before replacement; restored content uses the destination vault’s current key. Copying a system-mode profile directory alone does not copy its OS credential. Losing the OS credential store can make that local cache inaccessible; use a portable backup or resynchronise into a new profile. A password change rekeys the current database, not older backups. Recovery snapshots are not automatically pruned. **There is no passphrase recovery/backdoor.**

Markdown/JEX exports and exported attachments are deliberately readable external files; the UI labels them unencrypted. User-selected plaintext input files are not deleted or encrypted in place. No guarantee is made that arbitrary files a user saves inside the profile directory are encrypted.

### Network synchronisation

Network access occurs after the user configures an account and enables sync (plus the fixed public author link on explicit click). Automatic sync for newly configured accounts runs after opening and retries every five minutes while the vault is open. Closing an account-edit dialog without saving does not apply its draft credentials. No private server/domain is compiled into the product. Account credentials and cached sessions are stored inside SQLCipher; they are distinct from the vault passphrase. TLS verification remains enabled, TLS 1.2+ is required and redirects are disabled. HTTP is accepted only for `localhost` or loopback IP addresses for local testing. Credentials in URLs, query strings and URL fragments are rejected.

The sync implementation is experimental, uses complete snapshots, and supports only sync format 3, plain Markdown notes, notebooks, tags, relationships and resource payloads. It requests/renews an exclusive API lock for Joplin Server or a Joplin-compatible file lock for DAV. Nextcloud derives a private account Joplin folder from the server URL and encoded username; generic DAV accepts a dedicated notes URL. The collection must exist. Bounded DAV XML rejects DTDs, foreign-origin/out-of-directory hrefs, duplicate children and unsafe paths. PUT/DELETE use strong ETag preconditions; targets without suitable ETags cannot safely overwrite existing content. Conflicting writes fail with HTTP 412. Lock files provide cooperative exclusion; ETags additionally protect per-file overwrites with clients that do not honour them. Concurrent local/remote changes require explicit choices. Incoming changes have an encrypted recovery snapshot; local projection changes are transactional and baselines advance per successful step. A used target with missing metadata, or incoming deletions affecting at least 90% of local records, causes a fail-safe stop.

**Local SQLCipher encryption is not Joplin end-to-end encryption. Existing E2EE targets, malformed encryption metadata and encrypted note/resource content are rejected; encryption is never silently disabled.** Shared notebooks, HTML notes, interactive Cloud authentication/MFA/SSO and broad Cloud interoperability are not implemented. An HTTPS connection to an E2EE-disabled target protects transport, while the server can read the uploaded notes. No real Cloud account or personal notes were used during validation. No guarantee is made of complete conflict handling with every Joplin version or concurrent client.

### Untrusted content and bounded resources

SQL data uses bound parameters. The key/rekey PRAGMAs, which do not support binding, escape quotes into zeroized SQL buffers. No HTML/JavaScript execution or arbitrary shell/URL handlers. Markdown links are intercepted; only the fixed public About URL may be dispatched. Remote/file image requests are removed before rendering. Local PNG/JPEG attachments are decoded with dimension/allocation limits and re-encoded as capped thumbnails into memory-only bytes URIs. Image HTTP/file loaders are not enabled. Original attachments are never launched automatically.

JEX entries are never extracted to disk paths. Symlinks/special entries, unsafe paths, invalid identifiers/extensions, duplicate archive names, unsupported/encrypted records, missing resources and notebook cycles are rejected; import is transactional. Limits include 4 MiB note bodies, 32 MiB attachments, 256 MiB JEX payload/archive, 10,000 archive file records, 64 comma-separated tags per edited note, 100 text revisions per note and 500 rows per list page. Recovery drafts have a separate 32 MiB serialized cap. Image sources are limited to 4096×4096 and 64 MiB decoder allocations, with 1024-pixel thumbnails and four distinct local images per note. Sync snapshots are bounded at 10,000 records / 256 MiB and two minutes per attempt; individual HTTP requests have timeouts.

Native system text copy/cut/paste is enabled, including password paste. The OS clipboard may outlive the app and may be accessible to clipboard history/cloud sync or other processes; it is not claimed to be protected by SQLCipher.

Large imports/exports, backup, restore, rekey or migration can temporarily block their UI. Full-snapshot synchronisation and unpruned recovery copies still require performance/disk-usage work. These controls do not replace fuzzing, native Windows tests, independent cryptographic review or a full source audit. `cargo-audit` checks known Rust dependency advisories, not every possible C/OpenSSL vulnerability or application bug.

## Résumé en français

Les données de l'application sont désormais dans une base SQLCipher chiffrée : notes, pièces jointes, historique, brouillons, réglages, index et pages WAL. Par défaut, une clé aléatoire est gardée dans le coffre d’identifiants système ; le mot de passe maître est une option distincte. Le mot de passe du compte de synchronisation ne sert pas de clé locale. La protection système dépend de la session Windows et ne demande pas Windows Hello à chaque ouverture. En mode maître, la phrase n’est ni enregistrée en clair ni envoyée au service ; sa perte rend le coffre inaccessible. Les sauvegardes portables ont un mot de passe d’export dédié. Les exports Markdown/JEX et fichiers joints exportés restent lisibles et sont signalés comme non chiffrés.

La migration de l'ancien profil vérifie la copie chiffrée avant remplacement atomique. Elle n'efface pas physiquement les anciens blocs SSD, les sauvegardes externes ou les instantanés du système. Les anciennes sauvegardes gardent leur ancienne phrase. Les brouillons sont sauvegardés chiffrés avant verrouillage ; en cas d'échec de cette écriture, le verrouillage est bloqué afin de ne pas perdre le brouillon visible. Pendant une synchronisation, le masquage de l'interface est immédiat, mais la libération de la clé du travailleur attend la fin ou l'expiration de sa requête en cours.

La synchronisation Nextcloud/WebDAV et Joplin Server est expérimentale, automatique uniquement tant que le coffre est ouvert : HTTPS vérifié, identifiants dans le coffre, conflits à résoudre, copie de récupération et garde-fous contre les suppressions massives. **L'E2EE Joplin n'est pas implémenté ; une cible E2EE est refusée sans changement de sa configuration.** Une cible sans E2EE peut lire les notes reçues. Cloud interactif/MFA/SSO, partage et notes HTML ne sont pas pris en charge. Aucun compte réel n'a été utilisé pour les tests.

Rust et les limites d'entrée réduisent des risques ; ils ne garantissent pas l'invulnérabilité. Le stockage local chiffré ne protège pas un ordinateur compromis ni toutes les copies en mémoire/swap/presse-papiers. Voir les vérifications et limites dans VALIDATION.md et les fonctions restantes dans COMPATIBILITY.md.

## Reporting

Do not post private note contents, vault passphrases or account credentials publicly. Report suspected vulnerabilities through [GitHub private vulnerability reporting](https://github.com/jeremdevgit/carnet-rust/security/advisories/new). Dependabot alerts and security updates, secret scanning with push protection, RustSec dependency auditing and CodeQL analysis are enabled for this repository. A green check reports the result of a particular scan; it does not certify the application or guarantee that no vulnerability exists.

Ne publiez pas vos notes, phrases de passe ou identifiants dans un ticket public. Signalez une faille présumée par le [canal privé GitHub](https://github.com/jeremdevgit/carnet-rust/security/advisories/new). Les contrôles automatiques indiquent ce qu'ils ont effectivement analysé ; une coche verte ne certifie pas que le logiciel est exempt de failles.
